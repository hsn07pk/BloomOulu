# Runbook — Vipps MobilePay production go-live

**Owner:** Garden director (KYC) + engineering lead (config)
**Time budget:** Vipps merchant KYC takes 2–3 weeks. Engineering config: 1 hour after credentials arrive.

This is the rail that unlocks **true SCA-once recurring** donations from
Finnish + Norwegian + Danish donors. Paytrail's MobilePay path is one-off
only; the direct Vipps Recurring API integration is what carries the
annual/monthly tier model.

## 0. Pre-requisites

- A Finnish business entity (Y-tunnus). The University of Oulu's Y-tunnus
  works for the Garden.
- The Garden's bank account where Vipps will settle.
- A contact authorised to sign for the entity (the garden director or
  an authorised representative).
- A staging URL the Vipps onboarding team can reach for QA — typically
  `staging.bloomoulu.fi`.

## 1. Register a developer account + create a sale unit

1. Go to https://portal.vippsmobilepay.com/register/developer and create
   an account using the Garden's contact email. This step is free and
   immediate; it gets you the **test merchant** credentials.
2. In the portal, create a **sale unit** for "BloomOulu — University of
   Oulu Botanical Garden". Tick the **Recurring** product. Some Vipps
   features (eCom, login) won't be needed.
3. Submit the KYC bundle:
   - Y-tunnus + extract from the Finnish Trade Register (PRH-rekisteriote)
   - Beneficial-owner declarations for each natural person owning ≥ 25 %
     (this section is `non-applicable` for a state university — note it
     in the comment field and attach the University's constitutive
     statute)
   - The signer's Finnish BankID or analogous strong identification
   - Garden bank account number (IBAN) + bank-issued statement of
     ownership
4. Vipps responds within 5–10 business days. They may ask for an
   additional sample receipt + a sample MJML of the renewal email — both
   already generated by our worker; download from MailHog on staging.

## 2. Receive production credentials

Once approved, the portal exposes four secrets per sale unit. Treat all
four as **top secret** — never email, never paste into Slack.

```
client_id           = …
client_secret       = …
ocp_apim_subscription_key  =     ← this is "Ocp-Apim-Subscription-Key"
merchant_serial_number     = NNNNNN  ← MSN
```

A fifth value, the webhook signing secret, is set when you register the
webhook (step 4 below).

## 3. Configure BloomOulu

Production env via Doppler (or SOPS+age):

```
MOBILEPAY_API_URL=https://api.vipps.no               # production base URL
MOBILEPAY_CLIENT_ID=<client_id>
MOBILEPAY_CLIENT_SECRET=<client_secret>
MOBILEPAY_SUBSCRIPTION_KEY=<ocp_apim_subscription_key>
MOBILEPAY_MERCHANT_SERIAL_NUMBER=<MSN>
MOBILEPAY_WEBHOOK_SECRET=<set in step 4>
MOBILEPAY_RETURN_URL=https://bloomoulu.fi/fi/donate/complete
MOBILEPAY_CALLBACK_URL=https://api.bloomoulu.fi/webhooks/mobilepay
```

Restart the API + worker containers so they pick up the new env:

```bash
docker compose --profile prod up -d --force-recreate api worker
```

## 4. Register the webhooks

The Vipps Recurring API uses **webhooks per event type**. From the
merchant portal, register:

| Event | URL |
|---|---|
| `recurring.agreement-activated.v1` | `https://api.bloomoulu.fi/webhooks/mobilepay` |
| `recurring.agreement-stopped.v1`   | same |
| `recurring.agreement-expired.v1`   | same |
| `epayment.captured.v1`             | same |
| `epayment.aborted.v1`              | same |
| `epayment.failed.v1`               | same |
| `recurring.charge-failed.v1`       | same |
| `recurring.charge-refunded.v1`     | same |

For each, copy the **webhook secret** the portal generates and put the
SAME secret in `MOBILEPAY_WEBHOOK_SECRET`. (All events from a sale unit
sign with the same secret per our `MobilePayGateway` implementation; if
Vipps switches to per-event secrets in the future we'll switch to a
keyed lookup.)

## 5. Enable the rail

In `/admin/pages/settings`:

- `payments.mobilepay` = `true`

The provider router (`packages/payments/src/router.ts`) will start
preferring MobilePay for FI/NO/DK donors with `recurring=true`.

## 6. Smoke test (staging → production)

1. On staging, request an adoption with `preferredProvider=mobilepay,
   recurring=true`. Approve in the Vipps test app.
2. Verify in `/admin/resources/Payment`:
   - `Adoption.status=active`, `startedAt` is set.
   - `Payment.status=succeeded`, `providerPaymentRef` is the charge id.
   - Receipt PDF rendered + emailed.
3. Cancel the agreement via `POST /v1/adoptions/:id/cancel`. Verify the
   Vipps agreement is `stopped` in the portal.
4. Wait ~1 minute → re-check. The `agreement-stopped.v1` webhook should
   have flipped `Adoption.status=cancelled`.
5. Once staging is green, flip the flag on production. Run one real €25
   adoption through your own phone. Refund it from the merchant portal.

## 7. Renewal rollover (annual)

The `renewal` BullMQ cron runs daily at 04:00 UTC. For each
`Adoption.status=active && Adoption.recurring=true && endsAt < now + 7d`
it issues `chargeAgreement()`. Successful captures fire
`epayment.captured.v1` → `Payment.status=succeeded` → receipt +
email pipeline.

Failed charges trigger the dunning ladder (see
`apps/api/src/modules/jobs/processors/payment-retry.processor.ts`).
End donors hear about it via the `dunning-retry` / `dunning-paused` /
`dunning-cancelled` emails.

## Rollback

If something goes wrong:

1. `payments.mobilepay` = `false` in `/admin/pages/settings`. New
   adoptions skip the rail; existing recurring charges still settle.
2. For an individual recurring adoption you can stop the agreement
   directly from the merchant portal — the `agreement-stopped.v1`
   webhook flows back through and our handler marks the Adoption
   `cancelled`.
3. Refund any disputed charge from the portal; the
   `recurring.charge-refunded.v1` webhook updates `Payment.status` and
   issues a credit-note PDF.
